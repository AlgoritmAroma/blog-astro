# Astro AI — Блог

Два независимых Next.js-приложения в одном репозитории, делящие одну Postgres-БД:

```text
apps/
  blog/    публичный сайт для aiastro.ru — тёмный фон, золотой акцент #b8844c,
           шрифты Anticva/Involve, арочные карточки-«окна». Листинг и страница
           статьи, приём комментариев (на модерацию), счётчик просмотров.
  admin/   CMS: логин, CRUD статей, модерация комментариев. Простой
           функциональный UI, без брендинга основного сайта.
```

Разнесены намеренно — админка задумана как отдельный деплой на отдельном поддомене
(`admin.aiastro.ru`), закрытом IP-allowlist/VPN на уровне реверс-прокси, со своей
сессионной кукой, не расшаренной с публичным сайтом. Общий код между приложениями
(`db.ts`, типы, `format.ts`) — просто продублирован в обоих `src/lib/`, а не вынесен в
shared-пакет: для проекта такого размера npm-workspace добавил бы сложности (Docker build
context, hoisting, output tracing у Next.js) больше, чем сэкономил бы.

Оба — `output: "standalone"` (полноценный Node-сервер, не статический экспорт). Деплоятся
как два Docker-контейнера на одном VPS, оба смотрят в один и тот же Postgres.

## Разработка

Нужен реальный Postgres — проще всего поднять только `db`-сервис из compose:

```bash
cp .env.production.sample .env.production   # заполнить POSTGRES_PASSWORD (и остальное)
docker compose up -d db                     # postgres на localhost:5432

cd apps/blog && npm install
cd ../admin && npm install
```

Каждое приложение получает свой `.env.local` (скопировать `.env.production.sample` и
заполнить нужные ему переменные — `blog` не использует `ADMIN_*`/`SESSION_SECRET`, `admin`
использует всё).

Картинки в dev-режиме: `admin` пишет их в свою `apps/admin/public/uploads/`
(`covers/` — обложки, `content/` — картинки внутри статей), а `blog` отдаёт из своей
`apps/blog/public/uploads/` — в проде это один и тот же volume (см. `docker-compose.yml`),
а локально без Docker это два разных каталога, поэтому свежая картинка не отобразится на
блоге, пока обе dev-версии запущены раздельно. Проще всего один раз локально заменить
пустую папку симлинком:

```bash
rm -rf apps/blog/public/uploads && ln -s ../../admin/public/uploads apps/blog/public/uploads
```

Важно про `.env.local` в `apps/admin`: Next грузит его через `dotenv-expand`, который
воспринимает `$` как начало подстановки переменной. Bcrypt-хэш всегда содержит `$`
(`$2b$10$...`) — каждый `$` в нём нужно экранировать как `\$`, иначе хэш молча обрежется и
логин не сработает никогда (без явной ошибки). (В `.env.production`, который читает Docker
Compose через `env_file:`, экранировать не нужно — там нет подстановки переменных.)

```bash
cd apps/admin && npm run db:seed   # разово: заполнить БД исходными статьями
cd apps/blog  && npm run dev       # http://localhost:3000 — публичный сайт
cd apps/admin && npm run dev       # http://localhost:3001 — админка, вход на /login
```

## Как добавлять статьи

Через админку: `apps/admin` → `/posts/new` (нужен вход через `/login`). Там же
редактирование (`/posts/[id]/edit`) и модерация комментариев (`/comments`).

Тело статьи собирается конструктором из блоков: подглава (H2/H3 с выравниванием), текст
(с выделением жирным/курсивом и ссылками), маркированный или нумерованный список, картинка
с ALT и подписью, цитата, блок FAQ. Порядок блоков меняется стрелками, новый блок можно
вставить между любыми двумя. Отдельно у статьи задаются обложка с ALT, рубрика (из списка
или новая) и пастельный фон страницы.

Что уходит в поисковую выдачу:

| поле в админке | тег | если не заполнено |
|---|---|---|
| «Title для поисковика» (`posts.meta_title`) | `<title>` | берётся «Заголовок H1» |
| «Краткое описание» (`posts.excerpt`) | `<meta name="description">` | обязательное поле |

Заголовок H1 в `<title>` идёт по шаблону из `app/layout.tsx` — с добавкой
«— Блог Astro AI». Отдельный SEO-title подставляется как `absolute`, то есть **без** этой
добавки: он пишется под лимит выдачи (~60 символов), и дописывать к нему ещё 17 нечего.

«Время чтения, мин» (`posts.reading_time`) — необязательное. Пусто — оценивается по тексту
(≈180 слов в минуту), как было всегда; заполнено — показывается ваше число. На сайте
склоняется: `formatReadingTime` в `lib/format.ts` даёт «1 минута» / «3 минуты» / «5 минут».

## Просмотры

В БД счётчик честный, и поля для него в админке нет — только колонка в списке статей,
посмотреть. Раньше статья заводилась с 1000 просмотров и докручивалась руками; миграция
`reset-view-counts` обнуляет всё разом, а `posts.views` по умолчанию теперь `0`. Сохранение
статьи колонку не трогает (в `updatePost` её просто нет) — иначе правка текста сбрасывала бы
то, что насчитали читатели.

Считает `ViewTracker` на странице статьи: запрос в `POST /api/posts/[slug]/view`, а тот пишет
в куку `blog_viewed` (`2026-08-10|slug-one,slug-two`), что этому браузеру уже засчитано
сегодня. Повторное открытие и F5 в течение суток не считаются, другая статья — считается,
завтра — снова считается; кука живёт до ближайшей полуночи UTC. Это отсекает накрутку
перезагрузкой, но не человека, который чистит куки, — цель тут в том, чтобы колонка в БД
считала настоящие прочтения, а не в том, чтобы защититься от мотивированного накрутчика. Краулеры в счётчик не попадают: запрос уходит из JS.

**На сайте показывается не эта цифра, а она плюс базовый отсчёт 850–1000**
(`lib/views.ts`): «3 просмотра» под свежей статьёй работают против статьи, а прежний порог
`MIN_PUBLIC_VIEWS` просто прятал счётчик почти везде. База считается из slug'а (FNV-1a,
свёрнутый в диапазон), а не берётся случайно на рендере и не лежит в колонке — поэтому у
статьи она всегда одна и та же, в любом контейнере и на любом запросе, и никакой миграции
не нужно. Реальные просмотры копятся сверху; в админке видно именно их. Число склоняется
через `formatViewCount`: «851 просмотр», «1 234 просмотра», «1 205 просмотров».

Модель данных: блоки лежат в `posts.blocks` (JSONB), а `posts.content` хранит их
плоский текстовый слепок — по нему считается время чтения. У статей, созданных до
конструктора, `blocks` пустой, и блог рендерит их markdown из `content` через remark; при
открытии такой статьи в админке markdown автоматически разбирается на блоки
(`markdownToBlocks`), и первое же сохранение переводит её на новый формат.

Рубрики живут в таблице `categories`. Ничего не засеивается — рубрика заводится прямо из
формы статьи, когда она понадобилась. Восемь исходных рубрик, с которыми блог когда-то
поставлялся, удаляются одноразовой миграцией `drop-seeded-categories` (см. таблицу
`schema_migrations` и `RETIRED_SEED_CATEGORIES` в `lib/db.ts`) — но только те из них, за
которыми не стоит ни одной статьи, и только один раз: рубрику с тем же названием, заведённую
редактором заново, перезапуск контейнера уже не тронет.

**Безопасность.** Текст блоков — это HTML из `contentEditable`, и он попадает на публичный
сайт через `dangerouslySetInnerHTML`. Единственное, что стоит между ним и stored XSS, —
`sanitizeInlineHtml` в `src/lib/blocks.ts`: он пересобирает разметку с нуля, оставляя
только `strong/em/u/s/br` и ссылки с разрешённым протоколом. Санитайзер обязан вызываться
на сервере (это делает `parseBlocks` в Server Action). У него есть тесты:

```bash
cd apps/admin && npm run test:blocks
```

`src/lib/blocks.ts` продублирован в обоих приложениях (как и `lib/blog.ts`, `lib/db.ts`) —
при правке синхронизируйте обе копии.

`apps/admin/scripts/seed.ts` (`npm run db:seed`) — идемпотентный скрипт миграции:
переносит статьи из `apps/admin/src/content/posts/*.md` в БД (уже существующие slug'и
пропускает). Нужен один раз на свежей БД (локальной или на VPS) — на непустой безопасно
перезапускать.

## Деплой (Docker на VPS)

```bash
cp .env.production.sample .env.production   # заполнить реальные значения
sudo chown -R 1001:1001 uploads             # см. ниже — иначе загрузка картинок падает
docker compose up -d --build
docker compose exec admin npx tsx scripts/seed.ts   # разово, на свежей БД
```

**Права на `./uploads/`.** Контейнеры работают от пользователя `nextjs` (uid 1001), а
`chown` в `Dockerfile` отрабатывает до того, как поверх каталога встаёт bind-mount с
хоста, — так что владелец хостовой папки перебивает его. Если `./uploads` принадлежит не
1001, запись падает с `EACCES`, и в админке это выглядит как ошибка загрузки изображения.
Лечится один раз: `sudo chown -R 1001:1001 uploads`. Точную причину видно в
`docker compose logs admin` (строка `[upload] write failed:`).

Поднимутся два сервиса: `blog` на [http://localhost:8080](http://localhost:8080)
(публичный сайт) и `admin` на [http://localhost:8081](http://localhost:8081) (CMS) — порты
в `docker-compose.yml`. БД (сервис `db`, `postgres:16-alpine`) и `./uploads/` (обложки
статей, разделяемые между `blog` и `admin` через один volume-mount — админка пишет
обложки, блог их отдаёт) — volume-ы; без них любой передеплой стирал бы данные и
загруженные картинки.

На VPS перед контейнерами должен стоять свой реверс-прокси (nginx/Caddy) для TLS — этот
`docker-compose.yml` его не поднимает, только два приложения (8080/8081) и БД. Прокси
должен развести домены: основной домен → `blog` (без ограничений), поддомен админки →
`admin`, с IP-allowlist или VPN сверху — цель разнесения на два сервиса именно в том,
чтобы логин админки физически не был достижим из открытого интернета, а не в том, чтобы
просто сменить адрес.

**Размер загружаемых файлов задаётся прокси, а не приложением.** Потолок самой админки —
20 МБ (`MAX_UPLOAD_BYTES` в `apps/admin/src/lib/upload-constants.ts`); загрузка идёт
через Route Handler `/api/upload`, поэтому `serverActions.bodySizeLimit` из
`next.config.ts` к ней не относится и ничего не ограничивает. Зато у nginx
`client_max_body_size` по умолчанию равен ровно `1m`, и он отвечает `413` ещё до того,
как запрос дойдёт до Next.js — в админке это выглядит как «файл не долетел до сервера»
на любой фотографии с телефона. На vhost админки нужно поднять лимит выше приложения,
чтобы отлуп приходил из приложения с понятным текстом, а не голым `413` от прокси:

```nginx
# vhost админки
client_max_body_size 25m;
```

В Caddy отдельной настройки не требуется — он не ограничивает размер тела запроса по
умолчанию. Если перед прокси стоит Cloudflare, там свой потолок: 100 МБ на Free-плане.

Образы собираются на `node:22-slim` — не Alpine: `sharp` в этом проекте установлен только
с glibc-биндингом (без musl-варианта), на Alpine он не загрузится. `pg` (драйвер БД) —
чистый JS, к выбору базового образа отношения не имеет.

**Ссылки на основной сайт.** Основной сайт отдаёт каждый раздел дважды: публичная
страница (`/natal`) и рабочая, за логином (`/forecast/natal`) — его собственная шапка
переключается между ними ровно по этому префиксу, с теми же четырьмя названиями. Блог это
зеркалит (`src/lib/main-site-links.ts`): авторизованному читателю пункты меню ведут в
`/forecast/*`, а кнопка «Войти» превращается в «Профиль». Аноним получает публичные
страницы, а «Войти» ведёт на `/login?redirect=%2Fforecast%2Fnatal` — страница логина
основного сайта читает `?redirect=`, кладёт значение в `sessionStorage.redirectUrl` и
уходит туда после успешного входа, так что аутентификация из блога высаживает читателя в
прогнозе, а не на главной.

Авторизованность определяется наличием куки `accessToken` в запросе (`readerIsSignedIn` в
`src/lib/site.ts`). Внутрь токена блог не заглядывает и ничего на нём не авторизует — здесь
нечего авторизовывать, только выбор между двумя наборами ссылок. **Сейчас основной сайт
ставит эту куку как `accessToken=…; path=/` без `domain=`**, то есть host-only: она уходит
только на `aiastro.ru` и до `blog.aiastro.ru` не доезжает, поэтому проверка честно
возвращает `false` для всех, и блог ведёт себя ровно как раньше. Включается это одной
правкой на основном сайте — добавить `; domain=.aiastro.ru` в те места, где он пишет
`accessToken`/`refreshToken` в `document.cookie`.

**Dev и prod крутят один и тот же образ** (`main` → dev-сервер, `master` → prod, см.
`.github/workflows/`), поэтому всё, что у них различается, задаётся переменными окружения,
а не константами в коде. Ссылки шапки, подвала и хлебной крошки «Главная» ведут на
`MAIN_SITE_URL` — на dev-сервере это `https://dev.aiastro.ru` (подставляется в `.env` прямо
в `dev.yml`), не задана — `https://aiastro.ru`. Это намеренно **не** `NEXT_PUBLIC_`-переменная:
такие инлайнятся на этапе сборки, и прод-домен зашился бы в образ, из-за чего dev-блог уводил
бы читателя в прод. Значение читается на сервере при каждом запросе и передаётся в шапку
пропом (`src/lib/site.ts`), так что для его смены достаточно перезапустить контейнер.

## Шрифты и изображения

Шрифты `Involve` и `Anticva`, а также обложки (`apps/blog/public/images`) — фирменные
активы Astro AI, скопированные с основного сайта для визуальной консистентности блога.
Живут только в `apps/blog` — админка их не использует (простой системный шрифт, см.
`apps/admin/src/app/globals.css`).
